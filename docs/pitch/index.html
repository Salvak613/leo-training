Projet chef d'oeuvre, phase 1, point d'étape

Leo Training

Le hub des entraînements de la ligue LEO. Les centres publient leurs créneaux, les joueurs s'inscrivent en un clic, les places se mettent à jour en continu.

1 000 joueurs compétitifs Aujourd'hui : des Discord dispersés Un seul objet : le créneau
Quand je cherche où m'entraîner et que l'information est éparpillée sur les Discord de plusieurs centres, je veux voir au même endroit les créneaux ouverts et les places restantes, pour réserver ma place en une minute sans relancer personne. Formulation Jobs To Be Done, côté joueur

Étape B

Architecture

Multicouche classique. Routes, services, repositories, base. Testable et lisible pour une V1.
Front et back découplés. SPA React avec Vite, API REST Node et Express, JSON sur HTTPS.
TypeScript de bout en bout. Prisma et PostgreSQL, un contrat de données partagé.
Sécurité. Zod à l'entrée, Helmet, rate limit, JWT court et refresh token HttpOnly, bcrypt.
Sobriété. Pagination par défaut, payloads limités, pas de polling.

Étape C

Modèle de données

La capacité se compte sur les seules inscriptions confirmées
Dans une transaction avec verrou sur le créneau. Se désinscrire change un statut, ne supprime rien.
L'équipe d'un inscrit est dérivée, jamais stockée
Elle vient de son appartenance active. Aucune colonne en plus, aucune divergence entre les écrans.
MCD, MLD, MPD avec le DDL PostgreSQL complet
Seize tables, onze types énumérés, index uniques partiels pour le capitaine, l'équipe active et la vitrine.
